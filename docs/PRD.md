# Design QA — PRD

Версия: 1.0 · Дата: 12 октября 2026 · Статус: спецификация MVP для реализации.

Связанный документ: [TDD.md](TDD.md). PRD определяет поведение продукта и критерии приёмки; TDD — реализацию. При конфликте пользовательского поведения приоритет имеет PRD. Изменения согласованного объёма фиксируются одновременно в обоих документах.

## 1. Назначение и проблема

Внутренний сервис для дизайнеров и разработчиков одной команды. Сервис автоматизирует получение скриншотов и организацию ручного ревью вёрстки: сравнение с PNG-макетом, фиксацию замечаний, обсуждение исправлений и повторные проверки.

Сегодня макет, стенд, скриншоты и замечания находятся в разных местах. Команда теряет контекст: к какой версии сайта относится замечание, проверялось ли исправление, какой макет использован. Design QA хранит эту связь и позволяет вернуться к любой завершённой проверке.

Сервис не определяет автоматически, верна ли вёрстка. Решение принимает дизайнер. Совпадение пикселей не является критерием качества MVP.

## 2. Цели и измерение успеха

| Цель | Как проверить в пилоте |
|---|---|
| Собрать ревью страницы в одном месте | Все замечания выбранных пилотных страниц создаются и обсуждаются в сервисе |
| Уменьшить время подготовки сравнения | Замерить время от выбора страницы до открытия сравнения; целевой показатель — до 2 минут без ожидания очереди |
| Сделать повторную проверку прозрачной | Для каждого закрытого замечания видно, кто и в какой ревизии его закрыл |
| Сохранить доказательства | После загрузки нового эталона и повторного снимка предыдущая проверка открывается с прежними изображениями |

Пилот: 3–5 коллег, 2 проекта, не менее 10 вариантов страниц и 20 завершённых проверок. До запуска записать исходное время подготовки ревью; через две недели собрать обратную связь. Эти показатели — цели пилота, а не обещание производительности любого сайта.

## 3. Пользователи и доступ

- **Дизайнер:** создаёт структуру проекта, загружает эталон, запускает проверку, добавляет замечания, принимает исправления.
- **Разработчик:** открывает сравнение, отвечает, помечает замечание готовым к перепроверке, запускает повторный снимок.
- **Оператор сервиса:** разворачивает сервис, разрешает адреса стендов, задаёт сетевой доступ и профили доступа к закрытым страницам, делает резервные копии.

В MVP дизайнер и разработчик имеют одинаковые возможности. Разделение ролей описывает рабочий процесс, а не ACL. Приложение работает за корпоративным VPN/сетевым шлюзом. Собственной регистрации, паролей, организаций и ролей нет. Перед первой записью пользователь указывает отображаемое имя; сервер выдаёт идентификатор участника. Имя и идентификатор не подтверждают личность и не дают прав администратора.

Публичная публикация приложения не входит в MVP. Сетевой шлюз должен ограничивать доступ сотрудников; внешнюю систему SSO можно использовать перед приложением, но интеграция аккаунтов с продуктом отложена.

## 4. Границы MVP

### Входит

1. Проекты, страницы и варианты страницы с заданным viewport.
2. URL сайта на уровне страницы; вариант может переопределить URL.
3. Загрузка PNG-эталонов; история версий эталона, выбор текущего.
4. Серверный снимок первого viewport страницы через Chromium.
5. Очередь, прогресс задания, диагностируемая ошибка, повторный запуск.
6. Overlay с прозрачностью, slider с разделителем, side-by-side.
7. Zoom, pan, fit, масштаб 1:1, синхронное перемещение в side-by-side.
8. Прямоугольные замечания на снимке, текст, обсуждение, статусы.
9. Неизменяемые завершённые ревизии, история проверок и ручная перепроверка замечаний.
10. Ссылки на ревизию и выбранное замечание внутри сервиса.
11. Архивирование проекта, страницы и варианта без удаления истории.

### Не входит

- Figma OAuth/API и получение кадров по ссылке.
- Diff/heatmap, поиск ошибок, AI, анализ DOM, автоматическое принятие исправлений.
- Full-page снимки, прокрутка и автоматическое раскрытие элементов.
- Запись произвольных сценариев входа, пользовательский JavaScript, интерактивный браузер.
- Реальные мобильные устройства, другие браузеры, device emulation: mobile viewport — только узкое окно Chromium с тем же браузерным профилем.
- Jira/Slack/email, уведомления, экспорт отчётов, realtime совместное редактирование.
- SaaS, мультиарендность, подписки, сложные права, Kubernetes, Redis.

Viewport capture выбран для предсказуемой геометрии, ограниченного потребления памяти и быстрого MVP. Для длинной страницы в первой версии ревьюится только видимая верхняя область. Full-page — отдельное расширение.

## 5. Термины и сущности

| Сущность | Значение |
|---|---|
| Project | Группа страниц одного продукта |
| Page | Именованная страница и основной URL стенда |
| Variant | Viewport, настройки готовности страницы, текущий эталон, при необходимости отдельный URL и профиль доступа |
| BaselineVersion | Неизменяемая версия PNG-макета с размерами и автором |
| CaptureJob | Попытка получить снимок с замороженными входными параметрами |
| ReviewRevision | Успешная проверка: конкретный эталон, снимок, параметры захвата и дата |
| Issue | Обсуждаемое замечание с исходной ревизией и исходным прямоугольником |
| IssueReview | Состояние замечания в конкретной ревизии; при переносе может требовать уточнения положения |
| Comment / StatusEvent | Неизменяемые сообщения и журнал изменений статуса |

Ошибка захвата остаётся в истории заданий, но не создаёт успешную ревизию. Номер задания и номер ревизии — разные значения.

## 6. Основной сценарий

1. Дизайнер вводит имя, создаёт проект и страницу с разрешённым URL.
2. Создаёт варианты, например Desktop 1440×900, Tablet 768×1024, Mobile 375×812.
3. Загружает для каждого варианта PNG, экспортированный в масштабе 1×.
4. Нажимает «Создать проверку». Видит состояние: в очереди, снимается, готово или ошибка.
5. Открывает ревизию, переключает режимы сравнения, приближает область.
6. Рисует прямоугольник на снимке, вводит замечание. Оно появляется в списке и на холсте.
7. Разработчик открывает ссылку, отвечает и меняет статус на «Готово к проверке».
8. После выкладки исправления любой участник запускает повторную проверку от выбранной ревизии.
9. В новой ревизии дизайнер проверяет перенесённые замечания и закрывает исправленные либо возвращает их в работу.
10. Старые изображения и решения в старых ревизиях остаются доступными.

## 7. Функциональные требования

### FR-01. Структура проектов

Проект: имя 1–120 символов, описание до 2 000. Страница: имя, URL. Вариант: имя, ширина, высота, опциональный URL, профиль доступа, настройки готовности. Названия не обязаны быть уникальными; идентификация осуществляется по ID.

Списки показывают актуальную успешную ревизию, дату и число открытых замечаний именно этой ревизии. «Актуальная» означает успешно завершённую ревизию с максимальным номером; дата выполнения старого задания её не переопределяет. Новая версия макета или настроек отмечается как «Есть изменения после проверки».

Архивированный объект доступен в истории, но не допускает новых проверок и новых замечаний. Архивирование проекта распространяет запрет на потомков; разархивирование родителя не меняет собственный флаг архива у детей. Физического удаления через UI/API нет.

### FR-02. Viewport и эталоны

Ширина 320–2560 px, высота 320–1600 px, целые значения. Эти размеры — CSS-пиксели; снимок формируется в масштабе 1× и имеет точно такие же размеры в пикселях изображения.

PNG: до 15 MiB, одна статическая картинка, не более 2560×10000 px и 25,6 млн пикселей. APNG и другие форматы отклоняются. Эталон может иметь другую высоту, чтобы загрузить длинный макет; для MVP нужна только область, соответствующая viewport. Ширина PNG обязана совпадать с шириной варианта. Экспорт 2× необходимо заменить экспортом 1×; сервис не растягивает и не уменьшает эталон автоматически.

При загрузке макета выше/ниже viewport интерфейс предупреждает и показывает неперекрывающиеся области. Выравнивание обоих изображений — левый верхний угол. Прозрачные пиксели эталона сохраняются, фон просмотра — белый. Замена эталона создаёт новую версию. Переключение текущего эталона не меняет старые ревизии. Изменение ширины варианта сбрасывает текущий эталон, если его ширина больше не подходит.

### FR-03. Получение снимка

Проверка доступна при наличии подходящего эталона и разрешённого URL. В момент запуска фиксируются URL, viewport, эталон, настройки захвата и версия профиля доступа. Изменения варианта после запуска на задание не влияют.

Вариант позволяет задать CSS-селектор готовности (до 300 символов), дополнительную задержку 0–3000 ms и селектор ожидаемого авторизованного состояния для закрытого стенда. Нельзя задавать скрипты, заголовки или секреты через UI. Настройки по умолчанию: готовность документа, шрифтов и изображений в видимой области, затем пауза 300 ms.

Статусы задания: `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELED`. Пользователь видит понятную ошибку: адрес запрещён, нет доступа, превышено время, не найден элемент, не загрузились ресурсы, превышен лимит. Результат не заменяется пустым или частичным PNG. Необязательные сетевые ошибки записываются предупреждениями.

На один вариант допускается одно активное задание. Повторное нажатие не создаёт дубликат. Отмена разрешена только для задания в очереди. Ошибочное задание не перезапускается автоматически: «Повторить» создаёт новое задание.

### FR-04. Comparison Viewer

| Режим | Поведение |
|---|---|
| Overlay | Эталон над снимком; прозрачность эталона 0–100%, начальное значение 50% |
| Slider | Снимок слева, эталон справа; вертикальный разделитель 0–100%, исходно 50% |
| Side-by-side | Эталон слева, снимок справа; одинаковый zoom и сдвиг в координатах изображений |

Zoom 10–400%; «1:1» — один пиксель изображения на один CSS-пиксель экрана, «Вписать» — оба изображения полностью помещаются в доступные панели. Перемещение мышью/трекпадом; отдельные инструменты «Перемещение» и «Прямоугольник». Масштабирование сохраняет точку под курсором. При смене режима сохраняются центр просмотра и zoom, насколько позволяют размеры панелей.

Общий холст использует максимальную ширину и высоту пары изображений. Область вне одного из изображений имеет штриховку и подпись; она не интерпретируется как расхождение. Изображения не искажаются. PNG длинного макета загружается с ограничениями FR-02.

### FR-05. Замечания и комментарии

Прямоугольник создаётся в пределах снимка, а не эталона. В side-by-side рисование доступно только справа; прямоугольники показываются в обеих панелях на одинаковых координатах. В overlay/slider инструмент действует на координатную плоскость снимка независимо от видимого слоя.

Исходный прямоугольник замечания не редактируется. Неправильно выделенное замечание закрывается с пояснением; новое создаётся отдельно. В перенесённом замечании разрешено уточнить прямоугольник для новой ревизии; старое положение сохраняется в журнале.

Первое сообщение обязательно, 1–5 000 символов без учёта крайних пробелов. Ответы имеют те же ограничения. Текст — обычный текст, без HTML и вложений. Сообщения и авторские снимки имён неизменяемы; уточнения добавляются ответом. Все участники могут отвечать и менять статус.

Статусы замечания в ревизии:

- `OPEN` — требует исправления, включая повторно открытое.
- `READY_FOR_REVIEW` — разработчик считает исправленным.
- `RESOLVED` — участник проверил и принял исправление.

Разрешены переходы OPEN → READY_FOR_REVIEW/RESOLVED, READY_FOR_REVIEW → OPEN/RESOLVED, RESOLVED → OPEN. Для изменения нужен комментарий с объяснением; одно действие атомарно создаёт сообщение, событие и новый статус. Кто закрыл замечание, отображается явно; отдельного ограничения «только дизайнер» в MVP нет.

Список фильтруется по статусу, выбор сообщения подсвечивает область и центрирует её. Ссылка на замечание открывает его исходную либо указанную ревизию. Нет глобального статуса Issue вне ревизии.

### FR-06. Повторные проверки и неизменяемость

Повторная проверка запускается от явно выбранной ревизии того же варианта. При запуске копируется набор её незакрытых замечаний и их статусы. При завершении для них создаются IssueReview новой ревизии; изменения исходной ревизии после запуска не меняют копию. Закрытые замечания не переносятся, но видны в истории. Проверка без исходной ревизии начинается без переносов.

При одинаковом эталоне и одинаковых размерах снимка прямоугольник переносится без изменения. OPEN остаётся OPEN, READY_FOR_REVIEW остаётся READY_FOR_REVIEW; ни одно замечание автоматически не закрывается.

При смене эталона либо viewport все перенесённые замечания получают признак «Положение требует уточнения». Старый прямоугольник доступен для справки, но не рисуется как актуальная область. Дизайнер задаёт новый прямоугольник или закрывает замечание с пояснением. Координаты не пересчитываются пропорционально автоматически.

Неизменяемость относится к PNG, эталону, параметрам и метаданным завершённой ревизии. Новые сообщения, решения и положение перенесённого замечания — отдельная история событий; они могут добавляться и к старой ревизии. Обсуждение Issue общее между ревизиями, но у каждого сообщения указан контекст ревизии, а статус отображается отдельно для каждой ревизии.

## 8. Безопасность и эксплуатационные требования

Сервис принимает адреса только из списка, которым управляет оператор. Закрытые стенды разрешаются по точному hostname, порту и выделенному диапазону IP; доступ к произвольной внутренней сети отсутствует. Блокируются служебные адреса, loopback, metadata endpoint, PostgreSQL, MinIO и API сервиса. Те же правила относятся к перенаправлениям, iframe, шрифтам, изображениям и другим запросам страницы.

Для закрытых стендов MVP поддерживает заранее подготовленный оператором профиль с cookies/local storage либо HTTP Basic, привязанный к конкретному origin. Профиль выбирается по имени, секреты не отображаются и не попадают в API-ответы, изображения или логи. Интерактивный MFA и воспроизведение входа не поддерживаются. Истёкший профиль даёт понятную ошибку, без автоматического обхода защиты.

Изображения и комментарии считаются внутренними данными. Файлы доступны только через приложение за сетевым шлюзом. Доступ к MinIO извне закрыт. Не допускаются публичные ссылки на файлы.

Начальная эксплуатационная цель: до 10 одновременно работающих сотрудников, 1 активный снимок, очередь до 20 заданий, 2 000 ревизий. На согласованном тестовом сервере 4 vCPU/8 GiB API p95 ≤1 s без загрузки PNG; подготовленный тестовый стенд снимается ≤15 s без очереди. Общий лимит захвата 60 s. Просмотр пары 1440×900 открывается ≤3 s в LAN на обычном рабочем ноутбуке. Проверяется на фиксированных тестовых страницах, не на произвольном интернете.

Клавиатурой доступны основные кнопки, переключение режимов, список замечаний и изменение статуса; виден фокус. Создание прямоугольника допускается мышью в MVP. UI — русский, даты хранятся в UTC и показываются в локальном часовом поясе пользователя. Логи и ошибки имеют correlation ID.

Данные не удаляются автоматически. При достижении мягкой квоты 10 GiB изображений новые загрузки и проверки блокируются с инструкцией оператору; просмотр истории остаётся доступным. Ежедневные резервные копии PostgreSQL и файлов; целевой RPO 24 часа, RTO 4 часа. Эти цели подтверждаются пробным восстановлением.

## 9. Критерии приёмки

| ID | Проверка и ожидаемый результат |
|---|---|
| AC-01 | Создать проект, страницу и три viewport; после обновления браузера структура и параметры сохранены |
| AC-02 | Валидный PNG 1440×900 принят; JPEG под расширением PNG, APNG, PNG шириной 2880, повреждённый или превышающий лимиты файл отклонён без новой версии |
| AC-03 | Новый эталон создаёт версию B2; ревизия R1 продолжает ссылаться на B1 и тот же SHA-256 PNG |
| AC-04 | Снимок тестового стенда имеет ровно viewportWidth×viewportHeight пикселей; изменение варианта во время задания не изменяет его результат |
| AC-05 | Двойной запуск и повтор HTTP-запроса создают одно активное задание; второй независимый запуск получает ссылку на существующее |
| AC-06 | Overlay 0/50/100%, slider 0/50/100% и side-by-side показывают ожидаемые слои; изображения не растягиваются |
| AC-07 | Прямоугольник (100,200,300,100) сохраняет положение при zoom 50/100/200%, pan и переключении трёх режимов; ошибка обратного преобразования ≤0,5 px |
| AC-08 | Прямоугольник вне снимка отклоняется сервером; в области длинного эталона ниже снимка нельзя создать замечание |
| AC-09 | Сообщения, автор, даты, переходы статусов сохраняются; конфликт одновременных изменений даёт 409 и предложение обновить данные |
| AC-10 | R2 от R1 переносит только OPEN и READY_FOR_REVIEW; принятие замечания в R2 не меняет статус R1 и её PNG |
| AC-11 | Новый эталон/viewport при R3 отмечает перенесённые положения как требующие уточнения; исходные координаты сохранены, автоматического RESOLVED нет |
| AC-12 | Неуспешный захват оставляет FAILED с кодом и объяснением, не создаёт ReviewRevision; повтор создаёт другое задание |
| AC-13 | Разрешённый внутренний стенд доступен; запрещённые redirect, subresource, localhost, IPv6 loopback, metadata и DNS rebinding блокируются сетевым контуром |
| AC-14 | Два закрытых стенда в последовательных заданиях не получают cookies/Basic друг друга; истёкший профиль не выдаёт страницу входа за успешное ревью |
| AC-15 | После перезапуска воркера активное задание получает диагностируемый FAILED; очередь продолжает работать, дубликатов ревизий нет |
| AC-16 | Архив блокирует записи и новые проверки, сохраняя чтение; разархивирование снова разрешает работу с неархивированными потомками |
| AC-17 | Ссылка на ревизию/замечание открывает нужный контекст; наблюдатель видит изменения после обновления либо периодического опроса |
| AC-18 | Замерены цели раздела 8 на описанном стенде; при квоте/переполненной очереди новые операции отклонены, история доступна |
| AC-19 | После восстановления из резервной копии структура, сообщения и изображения контрольной ревизии доступны с прежними хешами |

## 10. Порядок поставки

1. Структура и файлы: проект → страница → вариант → эталон.
2. Безопасное получение снимков и история ревизий.
3. Viewer с тремя режимами и геометрией.
4. Замечания, обсуждения и статусы.
5. Повторные проверки, переносы и журнал событий.
6. Приёмка, восстановление и пилот.

Технические задачи и проверки каждого этапа находятся в TDD. MVP готов к пилоту после выполнения AC-01–AC-19; известные исключения должны быть явно согласованы, а не скрыты за статусом «готово».

## 11. Последующее развитие

Figma создаёт новые BaselineVersion через отдельный импорт; источник и версия кадра сохраняются. Full-page потребует нового режима захвата, лимитов и правил координат. Diff создаёт производный артефакт, не заменяя изображения. Автоматический анализ создаёт предложения замечаний с происхождением и уверенностью; дизайнер принимает их вручную. Авторизация и ACL вводятся до публичного доступа или подключения нескольких организаций.

Эти возможности учитываются через стабильные ID, версии, source metadata и отдельные операции; пустые интеграции и сервисы заранее не создаются.
